# C++ Coding Standards — DeviceHub (Qt6 desktop app)

Адаптировано из /Users/ilya/App/MyProject/CLAUDE.md для десктопного Qt6-приложения.
Действует для всего C++-кода в репозитории: DeviceHub (`src/`, `test/`) и
каждый микросервис в `services/<name>/` (свои `src/`, `test/`, `CMakeLists.txt`, `vcpkg.json`).

## Язык и стиль

- Целевой стандарт — **C++20**; предпочитать современные средства языка легаси-паттернам:
  - **concepts** (`requires`-ограничения) вместо SFINAE/`std::enable_if` там, где код действительно шаблонный;
  - **ranges** (`std::ranges`/`std::views`) вместо ручных циклов и пар итераторов — см. также раздел «Производительность и современные идиомы»;
  - designated initializers (`Foo{.field = value}`) — уже основной стиль инициализации структур/агрегатов в проекте, использовать и дальше вместо позиционной инициализации;
  - three-way comparison (`operator<=>`) для типов-значений, которым нужно сравнение/упорядочивание, вместо ручных `operator==`/`operator<`/… по отдельности;
  - `std::span` для передачи буферов (например, PCM-сэмплов, кадров) без владения вместо пары «указатель + размер»;
  - `constexpr`/`consteval`, structured bindings, `<format>` (`std::format` вместо ручной конкатенации строк/`QString::arg`-цепочек там, где формат сложнее одной подстановки).
- `[[nodiscard]]` — на методах, чей возвращаемый результат нельзя молча проигнорировать без потери корректности (геттеры, фабричные методы, методы, возвращающие `std::optional`/результат мутации) — сквозной стиль проекта, а не точечное решение по вкусу.
- Следовать ООП и **SOLID**, особенно Single Responsibility: классы делают одну вещь (например, `CameraDevice` не занимается рендерингом UI).
- Применять **DRY**, **KISS** — не городить паттерны там, где хватит простой функции.
- Предпочитать меньшее количество аргументов функций/методов: ориентир — не больше 3–4 позиционных параметров. Если параметров больше или они логически образуют одну сущность (например, `filename` + `contentType` + `dataBase64` + `sizeBytes` при загрузке вложения), группировать их в структуру-агрегат с designated initializers (`Foo{.field = value}`, см. выше) и передавать её одним аргументом, а не расширять список параметров дальше. Это же снижает риск перепутать порядок однотипных аргументов (например, несколько `std::string`/`int` подряд) на месте вызова.
- Предпочитать композицию глубоким иерархиям наследования; Qt-сигналы/слоты — основной механизм связи между слоями (устройства ↔ UI), а не прямые вызовы вверх по иерархии.
- Стиль Qt: `QObject`-наследники для классов с сигналами/слотами, `Q_OBJECT` макрос, `parent`-owned объекты для управления временем жизни (избегать ручного `delete`, где это можно доверить дереву `QObject`).
- **`switch` предпочтительнее цепочки `if`/`else if`**, когда сравнивается одно значение с несколькими константами (`enum class`, целое, символ) — читается и оптимизируется лучше; `if`/`else if` оставляем для разнородных условий, которые в `switch` не выражаются.
- Переменную, нужную только для проверки внутри `if`, объявлять прямо в нём (init-statement, C++17): `if (auto it = map.find(key); it != map.end()) { ... }`, а не заводить отдельной строкой до `if`, где она "утекает" в область видимости за пределами проверки.
- Предпочитать **RAII-обёртки** ручному управлению ресурсами — умные указатели (`std::unique_ptr`, как уже используется для `QAudioSink`/`QAudioSource`/`QCamera`), лок-гварды, файловые/сокетные обёртки с освобождением в деструкторе — вместо парных `acquire`/`release`, которые легко забыть вызвать на ветке с ранним `return` или исключением.

- Сборка всегда идёт с максимальным набором предупреждений и в pedantic-режиме: `-Wall -Wextra -Wpedantic` и остальные значимые предупреждения для GCC/Clang (`-Wshadow`, `-Wconversion`, `-Wsign-conversion`, `-Wnon-virtual-dtor`, `-Wold-style-cast`, `-Wcast-align`, `-Woverloaded-virtual`, `-Wnull-dereference`, `-Wdouble-promotion`, `-Wformat=2`, `-Wimplicit-fallthrough`), `/W4 /permissive-` для MSVC. Настраивается один раз в `CMakeLists.txt` на весь проект, а не точечно на отдельные цели.

## Структура

- **Один класс на файл** (пара `.h`/`.cpp`).
- Утилиты и хэлперы — всегда в отдельном файле, а не как приватные функции внутри класса, которому они сейчас нужны: в любой момент они могут понадобиться в другом месте. Оборачивать в именованный namespace по функциональной области (например, `namespace audio_utils { ... }`), не складывать в общий "utils" без области.
- Каталоги (DeviceHub):
  - `src/devices/` — доступ к железу (аудио, микрофон, камера, экран): `AudioOutputDevice`, `AudioInputDevice`, `CameraDevice`, `ScreenCaptureDevice`, `DeviceEnumerator`.
  - `src/auth/` — сетевой клиент к сервисам (`AuthClient`), асинхронно через сигналы, как и `devices/`.
  - `src/ui/` — Qt Widgets, ничего не знает о low-level API устройств/сети, только сигналы/слоты от `devices/`/`auth/`.
  - `test/` — GTest.
- Каталоги (микросервисы, например `services/auth-service/`):
  - `src/` — бизнес-логика и HTTP-слой сервиса, по тем же правилам (один класс на файл, хэлперы отдельно).
  - `test/` — GTest на бизнес-логику сервиса; интеграционные тесты между сервисами — где нужен реально запущенный второй сервис — пропускают себя (`GTEST_SKIP`), если он недоступен.

## Кроссплатформенность

- Бизнес-логика в `src/` собирается под macOS, Linux и Windows без правок. Платформенно-специфичный код — за интерфейсом с реализациями под каждую ОС (например, `IScreenCaptureBackend` + `MacScreenCaptureBackend`/`WindowsScreenCaptureBackend`/`LinuxScreenCaptureBackend`), а не разбросанные по бизнес-логике `#ifdef Q_OS_*`.
- `CMakeLists.txt` не хардкодит платформенные пути (например, `/opt/homebrew/...`); зависимости ищутся через `find_package`/`CMAKE_PREFIX_PATH`, платформенные значения приходят снаружи (переменная окружения, CMake presets), а не зашиты в файл.
- Новый код с обращением к ОС/железу (аудио, камера, экран, сеть) сразу проектируется с учётом, что под каждой ОС будет своя реализация — даже если на старте пишется и тестируется только под одну платформу.
- Если нужна внешняя библиотека — подключать через **vcpkg**, а не системный пакетный менеджер (brew/apt/...) или ручную сборку: так набор и версии зависимостей одинаковы на macOS/Linux/Windows и воспроизводимы в CI.
- vcpkg собирает Qt6 статически — плагины (permissions, sqldrivers, image formats и т.п.) не подключаются в рантайме сами, только те, что уже привязаны к используемым компонентам (Widgets/Multimedia). Новый плагин из другой категории — явно через `qt_import_plugins(target INCLUDE Qt6::...)` в `CMakeLists.txt`, иначе Qt тихо считает соответствующую фичу недоступной без единой ошибки в логе.

## Архитектура: клиент-сервер, подключение по Web-ссылке

- Приложение предоставляет серверную часть, к которой клиенты подключаются по ссылке (URL) — без обязательной установки нативного клиента для базового сценария просмотра.
- Сервер и клиент — отдельные модули/цели сборки с чётким сетевым протоколом между ними; не шарить внутренние структуры C++ через сеть напрямую.
- Ссылка на подключение сама по себе не даёт доступа — она работает вместе с авторизацией (см. «Безопасность»), а не заменяет её.
- Где это оправдано — независимо разворачиваемые части (авторизация, стриминг экрана, сигналинг) выносятся в отдельные микросервисы, а не растут одним монолитом; каждый — со своим сетевым интерфейсом, деплоится и масштабируется отдельно. Не дробить на сервисы то, что проще и дешевле держать вместе (см. KISS) — выносить, когда есть реальная причина: независимый деплой/масштабирование, разные нагрузочные профили, разная скорость изменения.
- У каждого микросервиса — свой манифест зависимостей vcpkg (`vcpkg.json`) рядом с его кодом, а не один общий на весь репозиторий: зависимости одного сервиса не должны тянуться в сборку остальных.

## Безопасность

- Любое подключение клиента к серверу проходит авторизацию по токену (например, короткоживущий подписанный токен, привязанный к сессии/ссылке); токены не логируются и не хранятся в открытом виде.
- Сетевой транспорт — только зашифрованный (TLS/WSS); открытые незашифрованные каналы допустимы только для localhost-разработки.
- Секреты (ключи подписи токенов, сертификаты, пароли) не коммитятся в репозиторий — только через переменные окружения или секрет-хранилище.
- Любые данные, пришедшие из сети (токены, сообщения протокола, параметры от клиента), считаются недоверенными и валидируются перед использованием.
- Пароли пользователей хранятся только хешированными современным алгоритмом для паролей (Argon2id и т.п.), никогда в открытом виде и не в самодельном хеше (обычный SHA-256 без соли — не пароль-хеш); хеш и подтверждение пароля не логируются.

## Производительность и современные идиомы

- Захват аудио/видео — асинхронный, через сигналы Qt (`QAudioSource`/`QAudioSink`/`QCamera`), не блокировать GUI-поток.
- Move-семантика вместо копий; `const&` для нетривиальных типов, `const` на методах, где не меняется состояние.
- `reserve()` для контейнеров, если размер известен заранее (например, список устройств).
- Стандартные алгоритмы/ranges вместо ручных циклов, где это не менее читаемо.

## Тестирование и документация

- Новые классы и методы получают **unit-тесты** (GTest — `test/`), включая тестируемую бизнес-логику отдельно от прямого обращения к железу (моки/интерфейсы для устройств там, где реальное железо недоступно в CI).
- Публичные классы/методы документируются **Doxygen**-комментариями (`@brief`, `@param`, `@return`).
- При добавлении фичи описание проекта в `README.md` обновляется в том же коммите/PR (не постфактум): что умеет приложение, как собрать и запустить — README не должен отставать от реального состояния проекта.

## Тестирование: производительность, безопасность, pentest, fuzzing

- Серверная/сетевая часть дополнительно покрывается **тестами производительности** (задержка, поведение под нагрузкой, множество одновременных клиентов) — отдельно от unit-тестов бизнес-логики.
- Точки, принимающие данные из сети (авторизация, токены, сообщения протокола), проверяются **тестами безопасности**: некорректные/вредоносные входные данные, попытки обхода авторизации, повторного использования токена и т.п.
- Серверная часть периодически проходит **тестирование на проникновение** (pentest) — оформляется как отдельная задача (issue) со своим номером, находки и фиксы трекаются как обычные баги.
- Где применимо — **fuzz-тестирование** (например, libFuzzer/AFL) для кода, разбирающего данные из недоверенных источников (сетевые сообщения, токены, файлы); в первую очередь на границе сервера с сетью.

## Диаграммы (PlantUML)

- Каждый новый класс и его публичные методы отражаются в диаграмме классов **PlantUML**: поля/методы, отношения (композиция, наследование, зависимость через сигналы/слоты).
- Диаграммы лежат в `docs/diagrams/`, файл `.puml` на функциональную область (`devices.puml`, `ui.puml`) — новый класс добавляется в диаграмму своей области, а не создаёт отдельный файл на каждый класс.
- Диаграмма обновляется в том же коммите/PR, что и код — не постфактум отдельной задачей.
- Для нетривиальных потоков (например, запуск захвата аудио/видео, обработка ошибок устройства) дополнительно делается **sequence-диаграмма**.
- Рядом с каждым `.puml` лежит его PNG-рендер того же имени (например `chat.puml` → `chat.png`) — `java -jar plantuml.jar -tpng docs/diagrams/*.puml`; перерендеривается в том же коммите, что и правка `.puml`. Оба файла — и `.puml`, и `.png` — перечислены в разделе «Диаграммы» README.md.

## CI (GitHub Actions)

- Каждое изменение — push в любую ветку и каждый PR — собирается и прогоняет **весь набор тестов** (`ctest`/GTest) в GitHub Actions; красный CI — блокер для мержа, а не то, что чинится потом.
- Workflow лежит в `.github/workflows/`; при добавлении нового тестового таргета в CMake он сразу включается в CI-шаг (`gtest_discover_tests` уже подхватывается через `ctest`, отдельно ничего перечислять не нужно).

## Git: задачи, ветки, коммиты

- Задачи ведутся в GitHub Issues репозитория (github.com/NekrasovIS/Exp) — номер issue используется в ветке и коммитах.
- Каждая фича перед реализацией (или вместе с ней) описывается: что делает, зачем, как использовать — в самом issue или в начале PR.
- Имя ветки включает номер задачи: `feature/<номер>-краткое-описание` (например `feature/42-camera-preview`), для багфиксов — `fix/<номер>-краткое-описание`.
- Каждый коммит начинается с номера задачи в квадратных скобках: `[42] Add camera preview widget`.
- Каждый баг — это отдельная задача (issue) с собственным номером, так же как и фича; фикс без заведённой задачи не коммитится. В задаче кратко описывается: как воспроизвести, что ожидалось, что происходит на самом деле.
- Номер этой задачи используется и в имени ветки (`fix/<номер>-краткое-описание`), и в начале каждого коммита (`[<номер>] Fix ...`) — по тем же правилам, что и для фич.
