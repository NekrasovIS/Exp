# Веб/мобильные клиенты (монорепо, issue #219)

См. [README](../README.md) за общим описанием проекта DeviceHub —
этот файл про монорепо `packages/`/`apps/web`, отдельное от десктопного
клиента и трёх backend-сервисов ([docs/services/](services/)).

Первый шаг к тонкому web-клиенту (issue #124/#220/#221) и мобильному
клиенту (issue #125/#222/#223, см. зонтичную задачу #214) — общий слой
доступа к бэкенду на TypeScript, который оба будущих клиента будут
переиспользовать один в один, без дублирования протокола REST/WebSocket.
Бэкенд (`auth-service`/`user-service`/`chat-service`) не меняется вообще
— это чисто клиентский слой, полностью отдельный от C++/Qt-части
репозитория (свой `package.json`/`node_modules`/`.gitignore`-записи, не
пересекается со сборкой DeviceHub/сервисов).

pnpm workspaces (`pnpm-workspace.yaml`):

```
apps/
  web/       React-клиент (issue #220, зонтичная задача — #264-#269,
             все подзадачи готовы): каркас/сессия/роутинг (#264), вход/
             регистрация/OTP (#265), сообщества/каналы (#266), чат
             канала (#267), друзья/личные диалоги (#268), шифрование
             каналов (#269), групповые звонки через Janus SFU (#221)
  mobile/    заглушка будущего React Native-клиента (issue #222/#223)
packages/
  core/      общий TypeScript-слой доступа к бэкенду — клиенты auth/user/
             chat-service (issue #248/#249/#250)
```

`apps/web` — Vite + React + react-router-dom. `SessionProvider`
(`src/session/SessionContext.tsx`) оборачивает `@devicehub/core`'s
`SessionManager`: держит токены в localStorage (сам `SessionManager` их
не хранит — см. его doc-комментарий), восстанавливает сессию при
загрузке страницы, планирует фоновое обновление access-токена.
`ProtectedRoute` — редирект на `/login` без валидной сессии. Живая
доставка сообщений — `useChatSocket()` (`src/chat/useChatSocket.ts`),
переиспользуемый хук над `ChatClient` из `packages/core`, подключается
при монтировании компонента с заданным `channelId`/`dmThreadId` и
отключается при размонтировании/смене — экраны из #265-#269 используют
его, а не заводят собственную WebSocket-логику. `currentLogin`
(`SessionContext`) — логин вошедшего пользователя, разобран из тела
токена на клиенте (`decodeTokenSubject.ts`) без обращения к
`/auth/verify`; используется только для UI-решений (например, «моё
сообщение или чужое»), не как проверка авторизации — каждый реальный
REST/WebSocket-запрос всё равно посылает сырой токен, и сервер
проверяет подпись сам.

`HomePage` переключается между двумя режимами (кнопка «Friends»,
как и в DeviceHub): обычный (сообщества → каналы → чат канала, #266/
#267) и режим друзей (`FriendsPanel` — заявки/друзья/добавление,
список диалогов, сам диалог — #268). Личные сообщения отправляются
через тот же WebSocket, что и сообщения канала (`ChatClient.sendMessage()`
— REST-метод `sendDirectMessage()` в `packages/core` существует для
полноты API, но не используется ни здесь, ни в DeviceHub: то же самое
делает `MainWindow.cpp`). Зашифрованные каналы (issue #136/#138)
поддерживаются и в веб-клиенте (issue #269) через `libsodium-wrappers`
(WASM-сборка того же libsodium, что и в C++-клиенте — байт-совместимые
`crypto_secretbox_easy`/`crypto_box_seal`, native WebCrypto для этого
не подходит: нет примитива XSalsa20-Poly1305 и нет стабильной
поддержки X25519 во всех браузерах). Идентити-кейпара (X25519,
`useIdentityKeys.ts`) — по логину, секретная половина не покидает
`localStorage`, публичная переопубликовывается при каждой загрузке
(идемпотентно, как и в `MainWindow.cpp`). При создании зашифрованного
канала (`ChannelsSidebar`, чекбокс «Encrypted channel») ключ канала
оборачивается для себя и для каждого участника сообщества с
опубликованным публичным ключом (`useEncryptedChannelSetup.ts`) —
участник без ключа пропускается, а не блокирует создание канала (то же
поведение, что и в DeviceHub). `ChatView` при открытии зашифрованного
канала запрашивает и расшифровывает свою обёрнутую копию ключа
(`useChannelKey.ts`) — отсутствие ключа на сервере и ошибка
расшифровки показываются одинаково («нет доступа»), без открытия
подписки/загрузки истории до этого момента.

Автокомплит @упоминаний (issue #326) — `useMentionAutocomplete.ts`
(общий хук для `MessageComposer` и `EncryptedChatViewContent`'s
собственного простого композера) детектирует триггер "@" по тому же
правилу, что и десктоп (начало слова, без пробела в наборе после "@"),
фильтрует логины участников сообщества и рендерит `MentionSuggestions`
— всплывающий список с клавиатурной навигацией (Up/Down/Enter/Tab/
Escape, обрабатывается `onKeyDown` самого поля ввода) и кликом мыши.
Список участников хук загружает сам через
`ChatRestClient.listMembers()` (уже существует в `packages/core` с
issue #250) — независимо от issue #322 (веб-список участников с
presence), который на момент написания этой фичи ещё не был смержен в
master. В зашифрованном канале упоминания набираются и резолвятся по
открытому тексту до шифрования — `encryptMessage()` вызывается только
над уже готовым телом сообщения в `handleSend()`.

Ответ/цитирование сообщения (issue #306/#331) — действие "Reply" в
`MessageList` доступно на любом сообщении, не только своём (в отличие
от Edit/Delete); строка "Replying to ..." с кнопкой отмены — над
композером (`MessageComposer`, и отдельно в `EncryptedChatViewContent`,
у которой свой собственный простой композер). chat-service хранит
`reply_to_message_id` как обычный nullable id, без снапшота автора/
текста оригинала (см. схему chat-service) — веб-клиент резолвит цитату
тем же способом, что и DeviceHub: поиском по уже загруженному
`messages`, с фрагментом текста, обрезанным до 60 символов. Ответ на
сообщение, которого нет в текущей загруженной странице истории (не
дальше "Load older messages", либо уже удалённое), показывается как
"Message unavailable" — эти два случая намеренно не различаются, тот
же принятый в issue #306 предел первой версии.

Реакции эмодзи на сообщениях (issue #305/#333/#335) — фиксированный
набор из 5 эмодзи (👍❤️😂🎉👏, тот же список, что и в `ChatMessageRow`
DeviceHub и в реакциях прямо во время звонка, issue #312), доступный на
любом сообщении в `MessageList`, а не только на своём — в отличие от
Edit/Delete, закрепление роли не требует. Клик по кнопке "React"
открывает набор эмодзи; клик по уже показанному чипу ("emoji count")
переключает свою реакцию тем же способом, что и явный выбор из набора
(`ChatClient.sendToggleReaction()` → кадр `{"toggle_reaction":
{"message_id", "emoji"}}`, тот же паттерн клиент-инициированной мутации
конкретного сообщения, что и у edit/delete). Наведение на чип
показывает список поставивших через `title` (нативный тултип браузера,
без отдельного UI-компонента). Живое обновление — `reaction_changed`
(`{"message_id", "emoji", "logins"}`, logins — ПОЛНЫЙ список после
переключения, не дельта) патчит соответствующее сообщение в
`useMessages()`: пустой список убирает чип целиком, а не показывает
"emoji 0". В зашифрованном канале эмодзи/логины реакций — открытый
текст на любом транспорте и так (chat-service не видит текст сообщения
ни в каком случае), поэтому `EncryptedChatViewContent` пробрасывает
`reactions` без отдельного шифрования/расшифровки.

Закреплённые сообщения (issue #308/#338/#340) — кнопка «📌 N» в
шапке чата (видна только если в канале хоть что-то закреплено)
открывает `PinnedMessagesPanel` со списком (автор, текст, кто
закрепил); клик по элементу списка прокручивает к самому сообщению в
`MessageList`, если оно сейчас загружено (`id="message-<id>"` у
каждой строки, `scrollIntoView()` — без запроса недогруженной
страницы истории, тот же принятый первой версией предел, что и у
`scrollToMessage()` в DeviceHub). Кнопки Pin/Unpin в `MessageList`
видны только модератору/владельцу (`useIsModerator`, тот же флаг, что
уже гейтит Delete — но независимо от авторства сообщения: закрепление
— действие управления каналом, а не модерации конкретного сообщения,
поэтому не появляется просто потому, что зритель сам автор). Список
закреплённых (`usePinnedMessages.ts`) загружается через REST
(`GET /channels/{id}/pinned-messages`) и обновляется живьём по
WebSocket-кадрам `message_pinned`/`message_unpinned` — `message_pinned`
запускает полный REST-рефетч (кадр несёт только id/pinnedBy/pinnedAt,
не весь текст, который нужен панели), `message_unpinned` удаляет
элемент локально без похода на сервер. В зашифрованном канале
(`EncryptedChatViewContent`) закреплённое сообщение расшифровывается
тем же ключом канала отдельным проходом от обычной истории — оно
может быть закреплено куда раньше, чем текущая загруженная страница
истории, и просто не входить в `decrypted`-карту, вычисленную для неё.

Подключение по ссылке (`/join/:code`, `JoinPage`, issue #301) —
завершает то, что оставалось в этом roadmap-маркере нереализованным
после самого факта существования веб-клиента: приглашение в сообщество
теперь можно прислать ссылкой, а не только сырым инвайт-кодом,
который нужно было вручную вставлять в форму. Ссылка — не новый
механизм, а обёртка вокруг уже существующего `invite_code`
сообщества (chat-service, issue #186/#256): `CommunitiesSidebar`
показывает ссылку `${origin}/join/<code>` для выбранного сообщества
(копировать может любой участник, перегенерировать — только владелец,
то же разграничение, что и в контекстном меню `CommunitiesPanel` в
DeviceHub). Без анонимного доступа — `/join/:code` для неавторизованного
посетителя только запоминает код (`sessionStorage`, не router state:
переживает переход на страницу регистрации и обратно) и уводит на
`/login`; сам вход в сообщество происходит уже после входа/регистрации,
когда `useCommunities()` тем же кодом автоматически вызывает
join-by-code (issue #301, продуктовое решение — без guest-режима
"посмотреть, не регистрируясь").

Бейджи непрочитанных сообщений (issue #310/#350) — тот же
chat-service-счётчик, что и в DeviceHub (issue #349, см.
[docs/services/chat-service.md](services/chat-service.md)): `useUnreadCounts()` (`src/chat/useUnreadCounts.ts`)
опрашивает `GET /unread` раз в 30с (плюс сразу при монтировании и по
вызову `refresh()` — `CommunitiesMode` зовёт его при переключении
сообщества), отдаёт `Map<id, count>` отдельно для каналов и для
диалогов ЛС. `ChannelsSidebar`/`CommunitiesSidebar` (сумма по каналам
сообщества, посчитанная в `CommunitiesMode` из карты `channelId →
communityId`, которая пополняется по мере открытия сообществ — то же
ограничение, что и у `channelIdToCommunityId_` в MainWindow.cpp: ещё не
открытое в этой сессии сообщество бейджа не покажет) и `DmThreadsList`
рисуют счётчик рядом с названием. В отличие от DeviceHub, у веб-клиента
уже есть постоянный список диалогов ЛС (`DmThreadsList`, issue #268),
поэтому им, в отличие от десктопа, бейдж всё же достался.
`useMessages()`/`useDirectMessages()` сами вызывают
`markChannelRead()`/`markDmThreadRead()` — сразу после начальной
загрузки истории (по последнему сообщению самой свежей страницы) и на
каждое живое сообщение, пришедшее по уже открытой WebSocket-подписке
(она держится только на открытом сейчас канале/диалоге, так что живое
сообщение всегда означает "прочитано прямо сейчас"); `onSelectChannel`/
`onSelectThread`/`openThreadWith` дополнительно вызывают
`clearChannelLocally()`/`clearThreadLocally()` из того же хука —
оптимистично гасят бейдж в интерфейсе, не дожидаясь ни завершения
запроса на сервер, ни следующего тика опроса.

Групповые звонки (`CallPanel`/`CallManager`/`useCall`, issue #221) —
кнопка «Join call» внутри `ChatViewContent`/`EncryptedChatViewContent`
(та же область, что и звонок в DeviceHub — привязан к каналу, не
глобальный). Публикация/подписка через тот же Janus videoroom SFU, что
и десктоп (issue #232) — тот же прокси-протокол chat-service
(`janus_attach`/`janus_message`/`sfu_room`/`janus_event`, теперь и в
`ChatClient` из `packages/core`), не отдельная mesh-реализация: участник
в браузере и участник в DeviceHub видят и слышат друг друга через одну
и ту же SFU-комнату. Аудио/видео — `getUserMedia`, демонстрация экрана
— `getDisplayMedia` (нативные браузерные API, без дополнительных
библиотек). Два отличия от десктопной реализации, оба — следствие
реальных ограничений браузерного API, не выбор: камера и демонстрация
экрана взаимоисключающие (десктоп может слать оба одновременно, issue
#185, потому что libwebrtc позволяет задать треку явный id при
создании, из-за которого подписчик отличает камеру от экрана уже после
прохождения через Janus — у `MediaStreamTrack` в браузере такого
конструктора нет, id всегда случайный); и если у desktop-участника оба
источника видео включены одновременно, браузерный подписчик увидит
только тот трек, чей `ontrack` сработает первым (см. doc-комментарий
`CallManager.ts` — тот же id-based механизм отличия камеры от экрана,
которого в браузере нет).

Лёгкие реакции эмодзи во время звонка (issue #312/#328) — ряд кнопок
быстрых реакций в `CallPanel` (тот же фиксированный набор из 5 эмодзи,
что и у `ChatMessageRow`/`CallWindow` в DeviceHub, `kCallReactionEmojis`
в `useCall.ts`) и всплывающий индикатор "<login> <emoji>" для входящих
реакций от других участников, автоматически скрывающийся через 2.5с
(`useCall`'s `lastReaction`, тот же интервал, что и десктопный
`CallWindow::kReactionFeedHideMs`). Кадр — `{"call_reaction":
"<emoji>"}` на отправку / `{"call_reaction": {"login", "emoji"}}` на
рассылку остальным участникам (никогда не эхо самому отправителю) —
тот же протокол, что уже реализован в chat-service и на десктопе;
`CallManager.sendReaction()` (apps/web) сам не отправляет кадр, если
сейчас не в звонке, вместо того чтобы разрешать chat-service отклонить
его с ошибкой, которую здесь всё равно негде осмысленно показать —
`ChatClient.sendCallReaction()` из `packages/core` сама по себе такой
проверки не делает (это уровень ответственности вызывающего клиента,
не протокольного слоя).

Черновики сообщений (issue #376) — `useMessageDraft.ts`, общий хук для
`MessageComposer` (канал, ключ `channel:<id>`) и `DirectMessageComposer`
(ЛС, ключ `dm:<id>`): несформатированный текст поля ввода сохраняется в
`localStorage` с дебаунсом 500мс (не на каждое нажатие клавиши),
восстанавливается при возврате к тому же каналу/диалогу (в том числе
после перезагрузки страницы) и удаляется сразу при успешной отправке.
Только веб — на десктопе актуальность ниже: то же окно/процесс не
размонтирует `ChatView` так же агрессивно при переключении канала.

Drag-and-drop вложений (issue #377) — перетаскивание файла из
проводника прямо в композер (`MessageComposer.tsx`) грузит его тем же
путём (`uploadFile()`), что и явный выбор через "Attach a file";
`onDragOver`/`onDragLeave`/`onDrop` на самой `<form>`, подсветка рамки
и текст-подсказка "Drop to attach" видны, только пока файл держат над
композером. `onDragLeave` игнорирует переход на дочерний элемент формы
(поле сообщения, лейбл вложения) — иначе подсветка мигала бы при каждом
микро-движении мыши внутри композера, поскольку `dragenter`/`dragleave`
всплывают с каждого элемента отдельно.

Требует Node.js ≥20 и pnpm (`corepack enable`, либо `npm install -g pnpm`
— версия закреплена в `package.json`'s `packageManager`). Команды из
корня репозитория:

```bash
pnpm install
pnpm build   # tsc -p tsconfig.json в каждом пакете
pnpm test    # vitest run в каждом пакете
pnpm lint    # ESLint (flat config) по apps/*, packages/*
pnpm format  # prettier --check по тем же путям
```

E2E-тесты (issue #303, `apps/web/e2e/`, Playwright) — отдельно от
`pnpm test` (Vitest+jsdom, логика компонентов/хуков): реальный Chromium
против production-сборки (`vite preview`, поднимается автоматически
конфигом Playwright), без живого backend'а — каждый тест сам мокает
свои сетевые вызовы через `page.route()`. Первый прогон должен сначала
скачать сам браузер:

```bash
cd apps/web
pnpm exec playwright install chromium
pnpm test:e2e
```

`eslint.config.mjs`/`.prettierignore` намеренно ограничены путями
JS/TS-монорепо — репозиторий также содержит C++/Qt-проект и
vendored-зависимости vcpkg в `vcpkg/`, которые не должны попадать под
эти проверки.
