# Возможности

DeviceHub — десктопное Qt6-приложение для работы с устройствами ОС
(аудио, микрофон, камера, экран), выросшее в клиент-серверный
инструмент для чатов/сообществ/звонков; см. [README](../README.md) за
общим описанием проекта и ссылками на остальную документацию. Полный
список реализованных фич — ниже.

- Список доступных устройств вывода звука и проигрывание тестового
  синус-тона на выбранном устройстве.
- Список микрофонов и захват с индикатором уровня входного сигнала.
- Список камер и превью выбранной камеры.
- Список экранов и захват содержимого выбранного экрана с превью.
- Вход по логину/паролю: получение и проверка токена авторизации через
  отдельные сервисы `auth-service` + `user-service` (Postgres).
- Вход по одноразовому коду через email или Telegram (issue #156/#174) —
  окно `LoginWindow` показывается при каждом запуске (токен между
  перезапусками пока не сохраняется): ввод логина/email/Telegram
  chat_id → код доставляется по одному из привязанных каналов (Telegram
  в приоритете, если привязаны оба) → ввод кода завершает вход. Требует,
  чтобы у аккаунта уже был задан email и/или Telegram chat_id (аватар в
  футере → `Edit Profile`, поля `Email`/`Telegram chat ID`); своей
  passwordless-регистрации нет, только для уже существующих аккаунтов.
  Второй шаг `LoginWindow` («Sign in with password instead») — вход по
  паролю или регистрация нового аккаунта, оба тоже закрывают
  `LoginWindow` и открывают главное окно при успехе; закрытие
  `LoginWindow` без входа завершает приложение.
- Чаты и сообщества: обмен сообщениями в реальном времени через
  `chat-service` (Postgres, WebSocket) — при открытии канала
  подгружается история сообщений, кнопка «Load older messages»
  подгружает более старые страницы.
- Подключение к сообществу по коду приглашения (issue #186): список
  иконок слева показывает только сообщества, в которых пользователь уже
  состоит — вступить в новое можно только зная его код (сервер отдаёт
  случайный 10-символьный код при создании, `GET /communities` без
  фильтра по членству больше не используется клиентом). Код виден
  любому участнику через «Copy Invite Code» в контекстном меню;
  «Regenerate Invite Code» (только владелец) делает прежний код
  недействительным.
- Desktop-уведомление (нативное OS, `QSystemTrayIcon`) о новом сообщении
  в открытом канале, пока окно DeviceHub не в фокусе — не показывается
  для собственных сообщений (`src/ui/DesktopNotifier`).
- Markdown-форматирование текста сообщений (**bold**, _italic_, `code`,
  списки, ссылки) — нативная конвертация Qt (`Qt::MarkdownText`), без
  своего парсера.
- Индикатор «печатает…» в открытом канале, пока собеседник набирает
  текст.
- Редактирование и удаление собственных сообщений (issue #107) —
  доступно только автору, с меткой «(edited)» на изменённых.
- Закреплённые сообщения канала (issue #308/#338/#339): "Pin"/"Unpin" в
  контекстном меню — виден только владельцу канала/сообщества или
  модератору сообщества (роль вычисляется на стороне клиента из уже
  загруженных данных сообщества/`GET .../moderators`, не хранится на
  сервере отдельно для UI). Кнопка "📌 N" в шапке канала (скрыта при 0)
  открывает список закреплённых сообщений — автор, фрагмент текста, кто
  закрепил; клик по элементу списка переходит к сообщению в истории,
  если оно уже подгружено. Закрепление уже закреплённого сообщения
  сохраняет исходного закрепившего и время первого закрепления, а не
  переписывает их — тот же принцип идемпотентности, что на сервере.
- Реакции эмодзи на сообщения (issue #305/#333/#334): подменю "React" в
  контекстном меню (доступно на любом сообщении, не только своём, в
  отличие от Edit/Delete) — фиксированный набор из 5 эмодзи. Под баблом
  появляется чип «эмодзи + счётчик» на каждую использованную эмодзи;
  клик по чипу — то же самое переключение (toggle), что и выбор той же
  эмодзи в меню. Наведение показывает список логинов, поставивших
  именно эту реакцию. Сервер отдаёт полный список после каждого
  переключения, а не дельту — клиент просто заменяет свою локальную
  запись для этой эмодзи целиком.
- Ответ на сообщение — reply/quote (issue #306): «Reply» в контекстном
  меню (доступно на любом сообщении, не только своём — в отличие от
  Edit/Delete) показывает над композером строку «Replying to
  <автор>: <фрагмент>» с кнопкой отмены; отправленное сообщение несёт
  только id оригинала (`reply_to_message_id`). Автор/текст цитаты для
  отображения резолвятся на стороне каждого клиента по собственному уже
  загруженному окну истории (`ChatView::messagesById_`) — chat-service
  не хранит и не отдаёт снапшот оригинала, а сама колонка
  `reply_to_message_id` в БД сознательно без внешнего ключа: удаление
  процитированного сообщения не блокируется и не портит его; сообщение,
  на которое ссылается ответ, но которое клиент не нашёл в своём кэше
  (удалено либо ещё не подгружено), показывается как «Message
  unavailable» — оба случая неотличимы друг от друга в этой версии.
  Начиная редактирование, отменяет незавершённый ответ, и наоборот — это
  два взаимоисключающих режима композера.
- Профиль пользователя (issue #110): отображаемое имя и ссылка на
  аватар, редактируются из «Account» → «Edit Profile»; футер и диалог
  показывают display_name вместо логина, как только он задан. Реальная
  загрузка/рендер картинки по avatar_url — за рамками этой версии,
  ссылка пока только хранится и показывается текстом.
- Роли и модерация (issue #114): владелец сообщества назначает
  модераторов («Manage Moderators…» в контекстном меню сообщества) —
  модератор может удалять чужие сообщения и переименовывать/удалять
  любые каналы сообщества, но не может редактировать чужие сообщения
  и не может управлять самим сообществом.
- Файловые вложения к сообщениям (issue #116, до 5 МБ) — кнопка
  «Attach» выбирает файл, загружает его на `chat-service` и сразу
  отправляет сообщение со ссылкой на вложение; у сообщения с вложением
  появляется кнопка «Download: <имя файла>» для сохранения на диск.
  Изображения (issue #188) дополнительно показывают миниатюру прямо в
  бабле — загружается автоматически в фоне, как только сообщение
  появляется в списке, не только по клику; видео пока получают только
  значок-заглушку с именем файла, без превью кадра.
- Автокомплит @упоминаний в композере (issue #326) — набор "@" в поле
  сообщения открывает всплывающий список участников текущего
  сообщества, отфильтрованный по уже набранным символам; Up/Down
  выбирают подсказку, Enter/Tab подставляют её, Escape закрывает
  список без изменений.
- Разделители дат (issue #188) — между сообщениями из разных
  календарных дней в истории канала появляется центрированная метка
  ("Today"/"Yesterday"/дата), в том числе перед самым первым показанным
  сообщением.
- Бейджи непрочитанных сообщений (issue #310/#349) — счётчик поверх
  аватара сообщества и жирный текст + "(N)" у канала в сайдбаре,
  посчитанные chat-service (см. [docs/services/chat-service.md](services/chat-service.md)), а не
  клиентской эвристикой (заменяет собой прежний подход issue #152).
  MainWindow вызывает `GET /unread` при входе, при переключении
  сообщества и периодически (раз в 30с) — без этого канал, на который
  клиент сейчас не подписан, никак не узнал бы о новом сообщении (у
  `WebSocketServer` нет живой push-доставки на неподписанный канал);
  открытие канала/диалога и получение в нём живого сообщения сразу же
  отправляют `POST /channels/{id}/read`/`POST /dm/threads/{id}/read`,
  так что счётчик не восстанавливается следующим опросом. Личные
  диалоги считаются на сервере тем же способом, но собственного бейджа
  в интерфейсе не получили — у DeviceHub нет постоянного списка
  диалогов ЛС, который можно было бы такой отметкой снабдить (диалог
  открывается кликом по другу в `FriendsPanel`).
- Поиск по сообщениям открытого канала (issue #118): кнопка «Search» в
  шапке канала открывает окно с полем запроса и списком совпадений
  (регистронезависимая подстрока по тексту сообщения); клик по
  результату прокручивает список к сообщению, если оно уже подгружено.
- Сквозное шифрование (issue #122). **Phase 1** (issue #136) — при входе
  клиент один раз генерирует локальную X25519-пару ключей (libsodium),
  приватная половина никогда не покидает машину, публичная публикуется
  через `user-service`. **Phase 2** (issue #138) — чекбокс «Encrypted
  channel» в диалоге создания канала («+» в панели каналов); создатель
  генерирует симметричный ключ канала и заворачивает его для себя и
  каждого текущего участника сообщества, у кого уже есть опубликованный
  публичный ключ (у кого нет — тост с предупреждением, доступа не
  получит, пока владелец/модератор не завернёт ключ для него отдельно).
  Заголовок открытого зашифрованного канала — с иконкой замка 🔒; тело
  сообщений шифруется на клиенте перед отправкой и расшифровывается при
  получении/загрузке истории — chat-service видит только шифротекст.
  Кнопки «Attach»/«Search» отключены в зашифрованном канале (вложения
  и серверный поиск пока не поддерживаются для него — см. [docs/services/chat-service.md](services/chat-service.md)
  chat-service ниже). **Довыдача ключа новому участнику** (issue #217)
  закрывает главный пробел Phase 2: правый клик на любом участнике в
  `MemberListPanel`, пока открыт зашифрованный канал (кроме собственной
  строки), предлагает «Grant channel key access» — оборачивает уже
  развёрнутый у вошедшего пользователя ключ этого канала под открытый
  ключ выбранного участника и публикует тем же `PUT
/channels/{id}/keys/{login}`, что и при создании канала; доступно
  любому участнику с уже развёрнутым ключом, не только владельцу (см.
  [docs/services/chat-service.md](services/chat-service.md)). Явная ошибка тостом, а не молчаливый
  no-op, если у самого вошедшего пользователя ключа этого канала ещё
  нет, или у выбранного участника ещё нет опубликованного открытого
  ключа. Известные ограничения этой фазы: нет forward secrecy
  (компрометация ключа канала = компрометация всей его истории), нет
  мультиустройственности.
- Личные сообщения и друзья (issue #187). **Фаза 1** — заявки в друзья:
  backend в `user-service` (`POST /friends/requests`,
  `GET /friends/requests`, accept/decline, `GET /friends`,
  `DELETE /friends/{login}` — см. [docs/services/user-service.md](services/user-service.md)). Взаимные
  заявки авто-принимаются в дружбу. **Фаза 2** — личные диалоги: backend
  в `chat-service` (`POST /dm/threads`, `GET /dm/threads`,
  `POST`/`GET /dm/threads/{id}/messages` — см.
  [docs/services/chat-service.md](services/chat-service.md)). Открыть новый диалог можно только с другом — chat-service
  проверяет это через внутренний вызов на user-service
  (`GET /internal/friendship`, см.
  `services/chat-service/docs/diagrams/dm-open-thread-sequence.puml`);
  уже открытый диалог продолжает работать, даже если дружба потом
  разорвётся. **Фаза 3** — UI в DeviceHub: кнопка «Friends» (значок
  друзей) сверху иконочной колонки сообществ переключает боковую панель
  и основную область в отдельный режим — список друзей и входящих
  заявок (`FriendsPanel`, правый клик — принять/отклонить заявку,
  расфрендить) вместо каналов, упрощённый диалог сообщений
  (`DirectMessageView`, без вложений/поиска/звонков/шифрования, которых
  backend этой фазы и не поддерживает для личных сообщений) вместо
  чата канала. **Фаза 2b** — живая доставка через WebSocket вместо
  поллинга: `WebSocketServer` chat-service принимает тот же
  Hello-протокол, что и для каналов, но с `{"token", "dm_thread_id"}`
  вместо `channel_id` (проверяет `ChatService::isThreadParticipant()`,
  404-стиль ошибка "no such thread" для не-участника — та же
  приватность, что и у REST-эндпоинтов `/dm/threads/{id}/messages`);
  после подписки единственный валидный кадр — `{"body"}`, рассылается
  обоим участникам диалога, включая отправителя (без звонков/typing/
  edit/delete — backend их для диалогов не поддерживает). На клиенте —
  отдельный экземпляр `ChatClient` (`dmChatClient_` в `MainWindow`,
  метод `connectToDirectMessageThread()`), не тот же, что подписан на
  канал сообщества (эта подписка нужна `CallManager` для сигналинга
  звонка).
- Голосовые сообщения (issue #359) — кнопка "🎤" рядом с "Attach" в
  композере: клик начинает запись с микрофона (`VoiceMessageRecorder`,
  собственный `AudioInputDevice`, независимый от общего, которым
  пользуются mic-тест в настройках и звонок), повторный клик ("⏹")
  останавливает и сразу отправляет как обычное вложение — WAV,
  собранный `audio_utils::encodeWav()` из накопленного PCM, тем же
  путём загрузки, что и файловые вложения (issue #116), без изменений
  на стороне chat-service. В бабле такое сообщение показывает "▶ Play"
  вместо ссылки "Download": клик скачивает байты (если ещё не скачаны)
  и сразу начинает воспроизведение через `QMediaPlayer`, повторный клик
  переключает Play/Pause. Не поддерживается в зашифрованных каналах —
  та же причина и то же отключение кнопки, что и у "Attach"/"Search".
